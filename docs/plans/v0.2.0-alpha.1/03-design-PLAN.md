# v0.2.0-alpha.1 / 03 — 독자 UI 디자인

상태: **D1·D2 작성 완료, 방향 선택 대기**. 현재 화면을 실제 브라우저에서 찍어 상태 지도를 만들었고, 비교 시안 두 개를 내놓았다. 사용자가 방향을 고르기 전까지 D3~D5와 [04](04-ui-independence-PLAN.md)의 화면별 적용은 시작하지 않는다. 구현도 승인도 아직 없다.

### D2. 시각 방향 두 가지

[비교 시트](https://claude.ai/artifact/95NZH2RBQtyCqwBbhepbiE)에 같은 대화·같은 상태(실행 중, 승인 대기, 질문)를 두 방향으로 그렸다. 색만 바꾼 복제가 아니라 정보를 쌓는 방식이 다르다.

- **A · 작업대** — 말풍선을 없애고 역할 표시와 가는 구분선만 남긴 기록형. 경로·명령·모델은 고정폭. 오른쪽 레일이 실행 상태와 한도를 항상 보여준다. 신호색은 사람이 답해야 하는 것에만. 한 화면에 턴이 약 1.6배 들어가지만 글은 빽빽하다.
- **B · 서술** — 본문 46자 폭, 넓은 줄 간격의 문서형. 역할은 본문 위 라벨 한 줄, 승인·질문은 왼쪽 띠를 댄 삽입 블록으로 글 흐름 안에. 상태는 문장으로, 한도는 머리글 칩 하나로 접는다. 길게 읽기 좋지만 스크롤이 늘고 한도는 한 번 눌러야 보인다.

### 사용자 결정 대기

[비교 시트](https://claude.ai/artifact/95NZH2RBQtyCqwBbhepbiE)의 "세 가지 결정" — 시각 방향, 기본 테마, 좁은 화면에서 먼저 보일 것 — 은 임의로 정하지 않는다. 답을 받은 뒤 D3(기준 폭별 시안)·D4(토큰·컴포넌트 명세)·D5(인계)로 넘어가고, 04의 5단계가 그 결과를 받는다.

## 목표와 경계

- AnA의 작업 흐름을 읽기 쉬운 독자적 시각 언어로 정리한다. 채팅, 사이드바, 입력, 보관, 승인, 질문, 작업 상태가 같은 규칙을 쓰게 한다.
- 색상, 글꼴, 여백, 밀도, 경계, 포커스, 피드백 상태를 토큰과 사용 예로 남겨 구현자가 임의로 해석하지 않게 한다.
- 데스크톱과 모바일에서 동일한 정보와 권한을 제공하는 반응형 시안을 만든다. 로드맵의 구조는 데몬이 호스팅하는 웹 UI 하나이며, 이후 Windows·Debian·Android 앱은 그 UI를 여는 얇은 셸이다.
- 이번 문서의 산출물은 리뷰 가능한 시안과 명세다. 컴포넌트 구현, shadcn 의존 제거, API/웹소켓 주소 변경, 네이티브 셸 제작, 단일 출처 호스팅 전환은 여기서 수행하지 않는다.
- 설정·사용량·예약 작업 등 전체 화면의 세부 통일은 로드맵상 v0.2 후속 알파 범위다. alpha.1에서는 핵심 흐름에 필요한 공통 규칙을 정의하고 후속 화면에 적용할 기준을 남긴다.

## 설계 원칙과 명세 범위

1. **정보 우선순위:** 사용자가 지금 해야 할 일(승인·질문·중단)과 실행 상태를 먼저 찾게 한다. 에이전트 본문, 도구 기록, 보조 메타데이터는 한 단계 낮은 계층에 둔다.
2. **행동 결과의 명확성:** 승인과 질문의 대상, 범위, 기한/기본 결과를 버튼 옆 문구로 설명한다. 위험을 단순한 빨간색이나 아이콘에만 맡기지 않는다.
3. **장문 내구성:** 긴 한국어 문장, 파일 경로, 명령, 코드 블록, 긴 작업명, 다수 작업 카드를 기준 사례로 그린다. 텍스트 확대 시 잘림이나 가로 스크롤을 검토한다.
4. **한 UI의 반응형 배치:** 화면 폭에 따라 사이드바·작업 상세의 배치를 바꿔도 채팅/승인/질문의 의미와 실행 권한은 유지한다. 플랫폼별 별도 화면 디자인을 만들지 않는다.
5. **접근 가능한 상호작용:** 모든 핵심 행동에 표시되는 레이블, 키보드 포커스, 상태 문자, 충분한 대비, 오류 복구 경로를 명세한다. 애니메이션은 움직임 줄이기 설정을 고려한다.

토큰 명세는 다음 묶음을 포함한다. 값은 시안 비교와 사용자 선택 뒤 확정한다.

| 묶음 | 산출할 토큰과 규칙 |
| --- | --- |
| 색상 | canvas/surface/elevated, text-primary/secondary, border, interactive, selected, info/success/warning/danger, focus. 밝은/어두운 테마별 값과 사용 금지 조합. |
| 서체 | 본문·제목·보조 정보·명령/경로의 글꼴, 크기, 줄 높이, 굵기, 숫자 정렬. 한국어/영문/코드가 섞인 예문. |
| 공간 | 4 또는 8 기반 여백 단계의 후보, 채팅 폭, 카드 내부 여백, 사이드바 폭, 대화 항목 사이 간격, 모바일 안전 영역과 터치 대상 크기. |
| 형태 | 모서리, 구분선, 그림자/층위, 아이콘 크기, 버튼 높이, 카드와 패널의 사용 기준. 장식 효과의 쓰임을 제한하는 예. |
| 상태 | 기본·hover·focus-visible·pressed·selected·disabled·loading·error·success·expired. 전송/중단, 승인, 질문, 작업에 대한 상태 표. |
| 움직임 | 새 메시지·상태 갱신·패널 열림의 지속 시간 후보, 움직임 줄이기 시 대체 표현, 상태 알림의 반복 억제. |

## 순서 있는 작업과 검토 가능한 산출물

### D1. 현재 흐름과 화면 상태 지도

- 입력: 위 코드 경로, [01 환경 계획](01-environment-PLAN.md)의 실행 환경, [02 안정화 계획](02-stability-PLAN.md)의 핵심 동작 기준.
- 작업: 채팅 전송→스트리밍→중단/완료, 워크스페이스 전환·보관/복원, 승인/질문 응답, 작업 상세 열기·닫기의 화면 상태를 표로 적는다.
- 산출: 사용자 행동, 표시 정보, 오류/연결 끊김, 키보드 초점 이동을 한 장에서 확인할 수 있는 상태 지도. 현재 구현과 시안에서 제안하는 변경을 구분한다.
- 완료 기준: 로드맵의 alpha.1 핵심 흐름 중 상태 지도가 없는 행동이 없다.

### D2. 시각 방향 비교와 사용자 선택안

- 입력: D1 상태 지도와 실제 콘텐츠 예문(긴 대화, 긴 명령, 다수 워커, 보관 목록).
- 작업: 차이가 설명 가능한 시각 방향 2개를 만든다. 각 방향은 같은 콘텐츠/상태의 채팅·사이드바 1쌍으로 비교하고, 색만 바꾼 복제안을 만들지 않는다.
- 산출: 방향별 라이트·다크 대표 화면, 핵심 토큰 표, 서체/밀도/강조 원칙, 장점과 읽기/공간상의 비용을 적은 비교 시트.
- 완료 기준: 사용자가 어느 방향을 선택하거나 구체적으로 수정할지 판단할 수 있다. 본 문서 작성 시점에는 선택·승인된 방향이 없다.

### D3. 핵심 시안과 상호작용 프로토타입

- 입력: D2에서 선택 또는 수정된 방향, D1의 동작 계약.
- 작업: 1440px 데스크톱, 768px 좁은 창, 360px 모바일을 기준 폭으로 잡고 필요시 중간 분기점을 추가한다. 각 폭에서 콘텐츠와 행동을 확인한다.
- 산출: (a) 채팅+사이드바 기본/검색/보관 상태, (b) 스트리밍과 중단, (c) 승인 대기·위험·만료, (d) 질문 선택·입력 오류·제출 중, (e) 작업 진행·완료·실패와 상세 패널의 시안.
- 산출: 클릭 가능한 연결 또는 명확한 화면 흐름 주석. 사이드바 열기, 질문 단계 이동, 승인 선택, 작업 상세, 모바일 입력 키보드 출현 시 동작을 보여준다.
- 완료 기준: 좁은 화면에서도 승인의 명령과 이유를 읽고, 질문에 답하고, 실행을 중단하고, 이전 대화를 찾을 수 있다.

### D4. 토큰·컴포넌트 명세와 접근성 점검

- 입력: D3 확정 시안과 [04 UI 독립 계획](04-ui-independence-PLAN.md)의 컴포넌트 경계.
- 작업: 토큰의 명칭/값/적용 예와 버튼·입력·메뉴·다이얼로그·메시지·카드·상태 표시의 변형 및 상태를 명세한다.
- 산출: 토큰 표(라이트/다크), 컴포넌트 상태 표, 포커스 이동 순서, 레이블/오류/상태 문구, 대비 확인표, 긴 텍스트·확대·움직임 줄이기 예시.
- 완료 기준: 구현자가 화면별 임의 색과 간격을 추가하지 않고 04의 컴포넌트를 만들 수 있다. 승인/질문 행동은 색 없이도 구분된다.

### D5. 구현 인계와 디자인 검토 기록

- 입력: D1–D4의 결과와 [05 릴리스 계획](05-release-PLAN.md)의 검증 게이트.
- 작업: UI 적용 우선순위를 공통 토큰/기본 부품→채팅·입력→사이드바·보관→승인·질문→작업 카드 순으로 적고, 기존 동작과 달라지는 부분을 명시한다.
- 산출: 화면별 주석, 토큰/컴포넌트 대응표, 사용자 선택 및 미결 항목 기록, 접근성 점검 결과와 구현 후 재검증 목록.
- 완료 기준: 04가 추측 없이 구현을 시작할 수 있고, 05가 시안 대비 회귀 여부를 확인할 수 있다.

## 검증 계획과 수용 기준

이 문서를 쓰면서 앱 테스트나 접근성 도구를 실행하지 않았다. 다음은 구현·검토 단계에서 기록할 명령과 수동 확인이다.

- 구현 후 apps/web에서 npm run lint, npx tsc --noEmit, npm run build를 실행하고 결과를 05의 게이트 기록에 연결한다. 명령 성공은 디자인 사용성 통과를 대신하지 않는다.
- 검토자는 데스크톱/좁은 창/모바일 폭과 라이트/다크에서 D3의 다섯 상태 묶음을 체크리스트로 확인한다. 긴 한국어 문장·경로·명령·다수 작업·200% 확대 사례를 포함한다.
- 키보드만으로 사이드바, 전송/중단, 승인 차단/허용, 질문 이전/다음/제출, 작업 상세 열기·닫기가 가능한지 기록한다. 포커스가 보이고, 대화상자와 패널을 닫은 뒤 합리적인 위치로 돌아와야 한다.
- 텍스트와 핵심 컨트롤의 대비를 토큰 조합별로 측정해 표에 남긴다. 의미가 색상에만 의존하지 않는지 확인하고, 상태 알림이 과도하게 반복되지 않는지 점검한다.
- 한국어 조합 중 Enter, 모바일 가상 키보드, 긴 대화의 입력·스크롤, 좁은 화면의 승인 명령 읽기를 실제 브라우저에서 확인한다. 결과가 없으면 통과로 표시하지 않는다.
- 수용 조건: 사용자에게 선택받은 시각 방향과 토큰이 문서화되고, D1–D5 산출물이 있으며, 위 핵심 흐름의 차단 문제와 접근성 문제를 해결하거나 05의 출시 판단에 명시한다.

## 위험과 되돌림

| 위험 | 대응과 되돌림 |
| --- | --- |
| 시각 변경이 실행 상태나 승인 위험을 가림 | D1 상태 지도와 동작 계약을 기준으로 변경 전후를 비교한다. 의미가 흐려지면 해당 표현을 기존 명확한 문구/배치로 되돌린다. |
| 데스크톱 시안만 완성되어 모바일에서 행동이 누락됨 | D3에 세 기준 폭과 가상 키보드 사례를 필수로 둔다. 모바일에서 핵심 행동이 빠지면 방향 확정을 보류한다. |
| 토큰이 기존 CSS와 중복되어 이행 중 화면마다 달라짐 | 04와 토큰 대응표를 먼저 합의하고 작은 화면 단위로 적용한다. 회귀가 생긴 화면은 이전 토큰 매핑으로 되돌린다. |
| 프로토타입 콘텐츠가 실제 긴 작업을 대표하지 못함 | D1의 실제 UI 필드와 긴 예문을 사용한다. 실사용 데이터로 확인되지 않은 가정은 주석으로 표시한다. |

## 사용자에게만 남겨 둘 결정

1. D2의 시각 방향 중 선택하거나 수정할 방향. 브랜드 색·강조 강도·정보 밀도·서체 인상은 비교 시안을 본 뒤 결정한다.
2. 기본 테마와 테마 전환 정책(시스템 추종, 밝음, 어두움 중 기본값). 현재 코드의 테마 존재가 기본 정책 승인을 뜻하지 않는다.
3. 모바일에서 처음 보이는 정보의 우선순위에 대한 선호: 작업 상태/승인 알림, 대화 본문, 워크스페이스 탐색 중 무엇을 가장 먼저 보길 원하는지. 기능과 권한은 동일하게 유지한다.

이 결정은 임의로 승인 처리하지 않는다. 결정 전에도 D1 상태 지도와 접근성 요구, 비교 시안은 작성할 수 있다.

## 바로 시작할 첫 작업

D1을 시작해 chat-page.tsx, composer.tsx, session-sidebar.tsx, approval-card.tsx, question-card.tsx의 현재 화면 상태와 행동을 한 표로 옮긴다. 각 상태에 사용자가 해야 할 행동, 표시되어야 할 정보, 오류·모바일·키보드 경우를 적고 02의 동작 기준과 대조한다.
